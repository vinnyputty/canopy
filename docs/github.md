# GitHub Issues connections

Canopy connects to GitHub.com using a fine-grained personal access token. Create one under GitHub **Settings → Developer settings → Personal access tokens → Fine-grained tokens**. Select the user or organization that owns the repositories, select only the repositories you want Canopy to access, and grant **Issues: Read and write**. Organization policy may require token approval.

In Canopy, choose **Connect Jira or GitHub → GitHub**. Enter the selected repositories as `owner/repo` names, separated by commas or spaces, and paste the token. Canopy verifies the account and issue access on each repository before saving the connection. An empty repository verifies successfully; a denied or missing repository produces an access error. The token is encrypted by the operating system credential store and stays in the Electron main process. Disconnecting removes the local token; revoke it in GitHub to invalidate it everywhere.

Open a repository root from the Open issue dialog, or enter `owner/repo` or a GitHub repository URL. It shows all issues in that repository, open and closed, with native sub-issues nested under their parents. Selected cross-repository descendants also appear under their parent. **Hide closed** hides closed leaf issues while retaining closed parents with visible children. You can also open an individual issue root using `owner/repo#number` or an issue URL.

Repository roots load up to 10,000 issues. Larger repositories show a size error; use an individual issue root or search to narrow the view.

Search shows matching selected repositories as roots and includes issue matches from up to ten selected repositories on each search page. **Search more repositories** continues through larger selections, while **Load more** appears when a repository has another page of matches. **Group by repository** in search results groups matches without changing the focused root tree. Every issue row shows its full repository and issue number. A child outside the selection appears as a warning; add that repository to the token and reconnect to include it. GitHub dependencies appear as directional links in the preview. The row menu and preview offer **Copy work brief**. Review the exact Markdown before copying; it retains the GitHub issue body and shows the provider-qualified issue identity, source, status, parent path, and dependencies when available.

The preview initially loads the newest comment page (up to 100 comments), shows the loaded range, and offers **Load older comments** one page at a time. Older-page errors preserve loaded comments and offer Retry. Loading older pages preserves recent-comment unread evidence and the last-seen baseline. Comment ranges reflect the issue count at preview load; comments added or deleted during paging may shift pages. Reopen or retry the preview to refresh that count.

The preview shows reporter, creation and update times, milestone, and issue fields. Open Development to load pull requests and commits referenced by the issue timeline; entries link directly to GitHub and show their available state. Branch associations are unavailable through this connection. A successful timeline read with no references shows an empty result; access failures show a retryable error.

Title, assignee, open/closed state, and labels are writable. Edit title, assignee, and state in the tree; edit labels in the issue preview. GitHub issues have no Jira priority, workflow transitions, or sibling ranking in Canopy. GitHub search is paginated by repository and returns at most the first 1,000 matching issues per repository, following GitHub's Search API limit. Truncated and incomplete responses are labeled by repository, including while more pages or repositories remain. Add specific title or body words to narrow a search, or enter a known `owner/repo#number` or issue URL and press Enter to open it directly within the connection’s selected repositories. Rate limits and authorization changes are shown as errors; retry after the displayed reset time or reconnect if the token was revoked.

Assignee search matches GitHub logins across repository assignable-user pages. Each typed search scans at most five pages of 100 users with a five-second deadline; an empty query browses one page. **Load more people** continues from the first unconsumed page. An incomplete search is shown separately from a completed search with no matches. Selection still verifies assignment eligibility for the selected issue’s repository.

The automated suite uses mocked GitHub responses for cross-repository hierarchy, pagination, writes, access failures, and rate limits. Live verification requires a token with Issues read and write access to two test repositories containing cross-repository sub-issues and dependencies. To share a token for local testing, save it in a file outside this repository and provide only the file path, repository names, and root issue reference.

## Changes since last seen

Canopy saves a local last-seen baseline after a successful tree load for up to 1,000 issues in each of the 12 most recently loaded roots. Later refreshes flag confirmed field changes and comment-count increases. The preview shows previous and current values and links recent comments whose creation times confirm they are new. Mark an issue seen in the preview or the root from the toolbar. Opening a preview and switching tabs preserve unread state; failed refreshes retain the baseline. Canopy's own successful edits update only their written fields in the baseline. Development updates and full provider history are unavailable in this view.

Issue relationship inspection reads [GitHub issue dependencies](https://docs.github.com/en/rest/issues/issue-dependencies), [sub-issues](https://docs.github.com/en/rest/issues/sub-issues), and GraphQL [`Issue.parent` and `Issue.relatesTo`](https://docs.github.com/en/graphql/reference/issues#issue). Related issues are typed provider relationships; labels, body references, and timeline mentions are not used as dependency evidence. Pagination is bounded and partial results remain explicit.

## Rich authoring

Open an issue preview and choose **Edit and discuss**. Description drafts use GitHub Markdown verbatim; Canopy displays it as escaped text. Description editing requires confirmed issue authorship or repository write access. Locked conversations require write access to comment. The token also needs Issues write permission; repository access alone cannot establish the token’s effective permission, so provider denials remain visible. Milestone choices require push access, include the first 100 open or closed milestones, and verify the returned value to detect silently dropped updates.

**Create sub-issue** creates in the parent’s repository and then attaches the issue by numeric ID. **Change parent** supports selected repositories under the same owner, including removal of a parent. It verifies ancestry and displays the issue leaving its old parent, joining its destination, and carrying its existing descendants. Apply checks the preview again and verifies the reported parent after writing. Repository transfers open in GitHub. Parent/create eligibility requires confirmed triage or write access on the relevant repositories; GitHub enforces its nesting, ownership, organization, and token restrictions.

Draft descriptions, comments, child titles/bodies, destination parent input, and uncertain-write markers persist locally by account and issue. A description revision conflict retains the draft and shows the current description for review. An explicit rejection allows correction and retry; an unconfirmed outcome blocks a new write until the user checks GitHub. A running request must settle before retry can be acknowledged. A reopened pane can save a newer text draft while that request runs; its completion preserves the newer draft. If creation succeeds but linking fails, the result names the created issue; preview that issue and use its parent editor to finish, without creating a duplicate. Refresh affected open trees after review.

Attachments hosted at GitHub’s user attachment or legacy user image URLs are discovered in the issue description and open through a provider-validated browser link. Uploads, Projects fields, additional milestones, and actions without confirmed capability use **Continue in GitHub**. Drafts are local application data, contain issue content, and persist across disconnect/reconnect of the same account; other accounts and issue keys cannot recover them.

Provider behavior is checked against the official [sub-issue REST API](https://docs.github.com/en/rest/issues/sub-issues) and [issue update REST API](https://docs.github.com/en/rest/issues/issues#update-an-issue). Controlled provider tests and the prepared desktop smoke use disposable fixtures without credentials. The authoring restart audit uses the shared `AuditOwner`, `deadline`, and `finishAudit` helper with a fresh owner for each launch and explicit caught-failure state. Pending launch, close, or audit operations retain the disposable profile; a timeout establishes failure and retains it through late settlement. Launch capture remains owned until acquisition settles, and restart requires the previous owner to close cleanly. After restart, it waits for the initial full page load before installing provider fixtures and reloading. The manual `//:authoring_check` entrypoint requires `CANOPY_APP_PATH` and `CANOPY_ELECTRON_PATH` from the verified staged bundle/runtime and the serialized desktop test token; live organization/token-policy acceptance is optional and separately authorized.
