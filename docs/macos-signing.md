# macOS signing candidates

Issue #77 implements an opt-in release route; it does not establish native qualification. Local packaging, pull requests and automatic tag-push drafts retain `mac.identity: null` and receive no signing secrets. **Prepare signed Canopy draft** (`sign-macos.yml`) is manual, runs only on an existing reviewed `v<version>` tag, and prepares an unpublished candidate with macOS 15 arm64 and Intel x64 DMG/ZIP downloads plus the existing Windows/Linux formats. Unsigned manifests cannot pass the public publication guard.

## External setup (pending authorization)

No Apple account, certificate, keychain, repository environment, secret, tag, release or cloud configuration was created by this implementation. Before any real signing run:

- [ ] Obtain an authorized Apple Developer Program Developer ID Application certificate and private key exported as password-protected PKCS#12. Choose a stable publisher Team ID/name; keep `app.canopy.desktop` stable across upgrades. Plan certificate renewal under that same publisher.
- [ ] Obtain an authorized team App Store Connect notarization API key (`.p8`), its ten-character key ID and issuer UUID. An individual key is outside this implementation's authentication contract.
- [ ] Configure the GitHub `macos-signing` environment with required lead reviewers, prevent self-review/bypass as appropriate, and restrict deployments to reviewed release tags. YAML naming alone creates no approval protection. Keep `public-release` separately protected. Source review and lead approval must precede dispatch, because tag code executes with environment secrets.
- [ ] Set environment variables `MAC_IDENTITY` (full `Developer ID Application: Publisher (TEAMID)`), `MAC_TEAM_ID`, `MAC_NOTARY_KEY_ID`, and `MAC_NOTARY_ISSUER`. Set environment secrets `MAC_CERTIFICATE_P12` (base64 of the export), `MAC_CERTIFICATE_PASSWORD`, and `MAC_NOTARY_KEY` (the PEM `.p8` contents). Keep these environment-scoped, not repository-wide. Do not enable debug/tracing or print credential payloads.
- [ ] Qualify the real hosted-runner import, builder, signing, Apple submission and cleanup contracts with authorized keys. Stubbed tests cannot establish those contracts on Apple systems.

Dispatch **Prepare signed Canopy draft** with the existing version tag as the workflow ref, after review/approval. There is no tag input that can redirect an unrelated branch to signing. The gate checks GitHub-hosted macOS, explicit opt-in, dispatch event, tag/package version, tagged commit, `GITHUB_SHA` and checkout HEAD. Inherited signing/debug configuration is rejected. `macos-15` supplies arm64 and `macos-15-intel` supplies x64; the final executable must have exactly the expected architecture. Other CPUs and universal builds are outside this route.

An unsigned draft created by the tag-push workflow occupies the same release tag. The signed route refuses to overwrite it. Inspect that draft and, only with later explicit authorization, remove the failed/unsigned **draft release** before dispatching the signed route. Retain the source tag. Never remove or overwrite a published release. Both routes remain drafts until native evidence passes the separate publication guard.

## Signing and verification contract

Secrets exist only in the signing step. The tool decodes the certificate and writes the API key into a private temporary directory. OpenSSL receives the real export password through a narrowly scoped environment variable; no real password or API key payload appears in process arguments. It converts the certificate/key to a temporary empty-password import container. The disposable signing keychain also has an empty password inside the private directory on the ephemeral gated runner; its password is not an authentication secret. The tool preserves/restores the runner's keychain search list, modifies only the temporary keychain, and attempts deletion and removal of all temporary credential files on both success and failure. Cleanup failure fails the signing step. Forced runner termination relies on hosted VM disposal; no persistent/self-hosted runner is accepted. Child output is captured and excluded from errors to prevent accidental key disclosure.

The exact valid Developer ID certificate name is required in that keychain. Its certificate SHA-1 becomes the explicit electron-builder v26 identity selector (`CSC_KEYCHAIN` points to the temporary keychain), and later certificate extraction pins every signature to it. Full prefixed identity names are rejected by the pinned builder's selector, so the configuration uses the certificate fingerprint. `forceCodeSigning`, hardened runtime, native per-CPU DMG/ZIP targets and DMG signing are enabled only for this path. Builder publication and automatic notarization are disabled; explicit notarization controls the ordering. The pinned builder supplies Electron entitlements and nested helper/framework signing.

The `afterSign` hook submits a temporary app ZIP using `notarytool --wait`, requires `Accepted` with a submission UUID, staples/validates the app, verifies its strict deep signature, publisher, certificate, bundle ID, secure timestamp, hardened-runtime flag, executable architecture and Gatekeeper assessment. Builder then creates the ZIP from the stapled app. ZIP archives have no independent codesign signature and cannot themselves be stapled. The signed DMG is submitted separately, must be accepted, and is stapled/validated and assessed as a signed disk image. The tool extracts the ZIP and mounts the DMG read-only, verifies both distributed app payloads, and detaches the mount in cleanup. The resulting trust report and SHA-256 hashes describe the final container bytes after stapling.

The credential-free packaged smoke then checks both exact downloads on each native runner and rejects a hash change against the signing report. Assembly requires both macOS architectures, a common publisher/certificate, complete verified trust records and all existing platform checks. `release-manifest.json` binds trust records to each exact filename/hash and source commit; draft upload is downloaded and checked again. Public publication requires a signed manifest, committed native evidence for the same bytes and publisher, and the existing live remote tag/version/commit checks. These JSON records are attestations from the reviewed pipeline, not a replacement for native signature verification or a cryptographic external provenance service.

## Installation and outstanding acceptance

For the matching CPU on macOS 15, verify SHA-256, mount the DMG and drag `Canopy.app` into `/Applications`, or extract the ZIP with Archive Utility and move `Canopy.app` to `/Applications/Canopy.app`. Open that installed app from Finder. macOS may show the ordinary first-open Internet download confirmation; exact wording and credential-Keychain prompts must be recorded during native qualification. No unidentified-developer/damaged-app warning or Gatekeeper bypass is acceptable. Do not clear quarantine or disable OS trust checks to produce evidence.

- [ ] Execute the real authorized signing/notarization workflow for both CPUs; inspect final certificate, strict signatures, hardened runtime, submission IDs, staples, Gatekeeper and uploaded hashes.
- [ ] On clean macOS 15 arm64 and Intel x64 desktops, browser-download each exact DMG/ZIP, retain quarantine, install and launch normally, record prompts and repeat offline using stapled payloads.
- [ ] Qualify upgrade from an explicit previous version/hash under the stable publisher; verify saved roots/preferences and authorized native Keychain credentials survive. Record the upgrade pair and any Keychain prompts.
- [ ] Complete install/relaunch/removal, native credential and other platform checks in [platforms.md](platforms.md); commit genuine exact-hash evidence using [releases.md](releases.md). Keep the release draft until all required checks pass and fresh review/lead approval permits protected publication.

## Primary contracts checked

The implementation uses the pinned electron-builder **26.15.3** configuration, including `mac.identity`, `mac.hardenedRuntime`, `mac.notarize`, `dmg.sign`, `afterSign` and `CSC_KEYCHAIN`; v27's reorganized signing configuration does not apply. The pinned installed builder source was also inspected for fingerprint selection and keychain behavior.

- [electron-builder v26 macOS configuration](https://www.electron.build/v26/docs/mac/) and [DMG signing](https://www.electron.build/v26/docs/dmg/).
- [Electron notarization authentication and hardened runtime](https://github.com/electron/notarize).
- [Apple notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) and [TN3147: notarytool migration](https://developer.apple.com/documentation/technotes/tn3147-migrating-to-the-latest-notarization-tool).
- [GitHub hosted runner CPU labels](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) and [environment protection/secrets](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

Local `//:macos_release_checks` uses mocked tool execution and a disposable tagged Git fixture. It exercises success/failure, secret-safe arguments/errors, certificate/publisher/CPU rejection, notarization/stapling/Gatekeeper rejection and cleanup. `//:release_checks` exercises matrix/hash/native evidence and live tag publication gates using synthetic bytes. Neither suite launches Electron, imports actual credentials, uploads to Apple or qualifies a release.
