# Managed AppImage hosted-CI installation

Managed installation, receipt cleanup and AppImage policy acceptance remain **unqualified**. Hosted Linux execution has passed secure installed-DEB first launch and restart. An earlier run refused the canonical root-owned `/opt` parent because it was group/other writable (`0777`); the cause of that mode is unknown. A subsequent run using the fixed `/var/lib` namespace refused loaded-profile identity during both prepare and cleanup and retained its fixtures. The mismatched attachment, mode or hash field is unknown. Reaching that refusal does not qualify the protected parents, policy inheritance, secure AppImage startup or cleanup. The Linux workflow opts into an app-specific installation on disposable Ubuntu 24.04 GitHub-hosted runners. Privileged execution requires independent source/security approval and authorized publication. It does not establish unmanaged portable execution or native acceptance.

## Policy contract and its limits

[Ubuntu security documentation](https://documentation.ubuntu.com/security/security-features/privilege-restriction/apparmor/#apparmor-unprivileged-user-namespace-restrictions) requires an application profile to permit unprivileged user namespaces. [Ubuntu's application-profile guidance](https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces) recommends vendors ship profiles attached to their installation paths. The [Ubuntu 24.04 release notes](https://discourse.ubuntu.com/t/ubuntu-24-04-lts-noble-numbat-release-notes/39890) describe `flags=(unconfined)` with `userns,` as an application-specific permission.

The static profile attaches only to the immutable original runtime:

```apparmor
abi <abi/4.0>,
include <tunables/global>
profile canopy-appimage /var/lib/canopy-appimage-ci/Canopy.AppImage flags=(unconfined) {
  userns,
}
```

This grants namespace access to the named profile; it is not a filesystem confinement profile. Children can inherit its permission. The exact attachment path alone does not limit permission to one executable throughout the process tree.

[AppArmor's kernel domain-transition implementation](https://github.com/torvalds/linux/blob/v6.8/security/apparmor/domain.c) retains the current unconfined profile on exec when no other attachment matches, and changes labels when another profile attaches. This is conditional inheritance, not a guarantee for every installed interpreter or runtime. The [upstream AppArmor inheritance report](https://gitlab.com/apparmor/apparmor/-/issues/527) describes the same behavior, but a report is not proof of Canopy's effective label on a particular runner.

Canopy's `AppRun` uses a Bash interpreter and execs the mounted payload. A successful profile load or permission on the original AppImage therefore cannot alone establish permission in the actual FUSE-mounted Electron process. The runner's loaded profiles, exec transitions and effective process context must be checked. A SUID-helper fatal message does not establish mounted helper ownership/mode or an AppArmor denial.

## Installation and launch requirements

The managed source enforces these requirements:

- Copy the original artifact to `/var/lib/canopy-appimage-ci/Canopy.AppImage`, preserving its exact SHA-256 and executable bytes. Require root ownership and no group/other write permission on the file and every parent; reject symlinks and unexpected existing destinations. Do not change mounted or extracted helper ownership or SUID permissions.
- Create an exclusive root-owned installation receipt binding the source artifact hash, destination identity, exact profile content/hash and resources created by this installation. Refuse any existing profile file or loaded profile with the same name; do not replace another installation's policy.
- Load only the exact app-specific profile. Verify its loaded identity and attach it through ordinary-user execution of the fixed original runtime. Keep global AppArmor/sysctl settings, mounting semantics, format selection, Chromium arguments and launch deadlines intact.
- Bind the sole actual direct launch to its retained `ChildProcess`, parent, birth, UID and canonical original executable before accepting mounted evidence. Validate live FUSE executable/ASAR hashes, mount identity, helper containment and effective AppArmor context across exec. A cached command, PID, expected hash or extracted tree is insufficient.
- Verify sandbox-enabled first-run and restart with the same credential-free isolated profile, persisted appearance, renderer `NoNewPrivs: 1`/`Seccomp: 2`, and executable/ASAR identity. Preserve fail-closed behavior when policy, FUSE, launch binding or sandbox checks fail.
- On every attempted installation, use bounded cleanup tied to the receipt. Remove only owned, unchanged resources and unload only the installation's exact profile after the launch is finished. Refuse mismatched ownership, paths, identity or policy content. Preserve a primary failure if cleanup fails; cleanup failure after otherwise successful checks fails the gate.

`CANOPY_MANAGED_APPIMAGE=1` requires actual Linux x64, an ordinary audit UID, GitHub Actions hosted/Linux/X64 metadata, numeric run/attempt, `ImageOS=ubuntu24`, an image version, a canonical GitHub workspace and actual Ubuntu 24.04 OS metadata. The caller checks before invoking `sudo`; the private root entry repeats the guard and requires the corresponding `SUDO_UID`. Local, self-hosted and nonmanaged paths never opt into this recipe. Environment metadata is an operational guard on the trusted disposable workflow, not cryptographic runner attestation.

The caller selects the currently executing Node binary through Linux `/proc/self/exe`, requiring a canonical regular executable with matching file identity and SHA-256 before invoking the fixed private module. Resolution and hashing consume the original twelve-second transport deadline. The sudo environment contains only fixed `PATH`/`LANG` and the explicit hosted operational allowlist; it excludes Bazel wrapper variables and `NODE_OPTIONS`. This relies on the trusted reviewed toolchain and source, and does not promise atomic immutability against a hostile same-UID actor. Unreadable, changed or mismatched executable evidence is uncertain and refuses invocation and cleanup.

The private helper exposes only prepare/check/live-launch/cleanup operations for the fixed paths. It uses exclusive root-owned creation, a `0600` receipt at `/var/lib/.canopy-appimage-ci.json`, a `0555` original and a `0444` policy. Original copy reads refuse symlinks and root-owned sources and use finite streaming bounds. Receipt records bind run/attempt/token, ordinary parent/birth, source identity/SHA, inspected payload/helper expectations, created resource identities/hashes, protected parents and exact policy content. Partial-copy/write failures repair only recorded exclusive resources; unverifiable receipt repair retains resources and fails cleanup.

The four owned resources are the exclusive root-owned `0755` directory `/var/lib/canopy-appimage-ci`, its original runtime, the receipt and the fixed policy file. The helper independently checks and pins `/`, `/var`, `/var/lib`, `/etc` and `/etc/apparmor.d` as canonical root-UID/root-GID directories without group/other write or set-ID bits. Receipt validation rechecks every pin; the observer's original-parent chain includes `/`, `/var`, `/var/lib` and the owned directory, and the consumer requires those identities to match the receipt and directory resource exactly. Unprotected parents and preexisting destinations are refused without repair. The helper neither migrates nor removes former `/opt` resources; former receipts and policy attachments supply no current authority. Existing policy files or loaded profiles block preparation. The installed-DEB executable remains `/opt/Canopy/canopy`.

The [AppArmor parser reference](https://www.apparmor.net/man/4.0/apparmor_parser/) documents single-profile add/remove, an explicit config file and cache suppression. [Linux 6.8 AppArmor introspection](https://github.com/torvalds/linux/blob/v6.8/security/apparmor/apparmorfs.c) exposes profile name, attachment, mode and `sha256` (64 lowercase hexadecimal characters plus newline); unavailable introspection is a blocker. Only `/usr/sbin/apparmor_parser --config-file=/dev/null --skip-cache --jobs=0 --add` or `--remove` receives the single fixed policy file. No replacement, cache write, wildcard attachment or global configuration operation is used. Loaded name, attachment, mode, kernel `sha256` and identity must match the receipt. Missing kernel policy introspection fails closed. AppArmor enabled state and both user-namespace restriction sysctls are retained and compared before/after verification and cleanup.

The [AppArmor 4.0.1 parser](https://gitlab.com/apparmor/apparmor/-/blob/v4.0.1/parser/parser_main.c) executes work inline with `--jobs=0`, avoiding its default compilation-worker fork for this single profile. Before add/remove, the root receipt records the actual helper writer and pending mutation; successful spawn/birth and actual command exit/closure are required before recording terminal proof. A pending or malformed proof blocks independent cleanup even when no profile is currently loaded.

The private helper retains its ten-second self-deadline, the parent transport a twelve-second failure deadline, and the asynchronous parser a five-second failure deadline. Deadlines are failure bounds, not termination guarantees. Each operation has one absolute monotonic expiration covering setup/spawn; readiness, terminal proof and application-close success check elapsed time even if the timer callback is delayed. A timeout, child/request/output-stream fault or unproved closure detaches owned pipes and refuses acceptance; a later zero exit cannot turn it into success. The native root helper may signal only its actual confirmed parser child; the ordinary caller does not attempt to kill root helpers. Transport requires a bounded non-null envelope with complete typed operation-specific success data or a complete typed failure. Success validates the emitted receipt serialization hash, finite file identities, scoped resources, global/load state, coherent parser writer/child/terminal proof and launch payload/mount/helper identities before the wrapper can continue. The parent rechecks the same expiration after validation and terminal/status coherence, immediately before accepting success or classifying a failure as known. Malformed replies, serialization/write faults and request-stream errors are uncertain, stopping further verification and additional privileged cleanup even before a receipt exists. Complete known failures remain eligible for guarded cleanup. A prior live/unreadable helper or uncertain mutation retains the receipt/resources because it can still apply policy. No synchronous parser call blocks the helper timer. No arbitrary PID or product kill is performed. Cleanup checks receipt/file/policy identities and a bounded privileged inventory of process executables and thread labels. A live managed original/profile, unreadable live task, changed process, unknown policy ownership or unowned directory entry blocks unload/removal and retains evidence/resources on the disposable runner. A vanished proc directory is distinguished from an unreadable live process. Failed managed checks retain their disposable user-data/extraction fixture directory; they do not delete it on the strength of `app.close()` alone. These sequential checks do not promise an atomic inventory or protect against a hostile privileged actor.

First managed acceptance consumes the completed observer snapshot and matches its retained/native root to the actual `ChildProcess` returned by Playwright, plus the effective live main process. Both first run and restart require ordinary UID/birth, original mount source, mounted ELF/ASAR/helper SHA, helper ownership/mode, exact main/renderer effective profile and renderer `NoNewPrivs: 1`/`Seccomp: 2`. Missing, incomplete, unknown or mismatched evidence fails before verified packages are copied. Download and copied-download hashes must match the exercised original. Cleanup failure fails an otherwise successful gate; boolean failure state preserves even falsy primary exceptions, including failures in secondary diagnostic formatting or logging. Scoped `SIGINT`/`SIGTERM` handlers reject acceptance even if the callback is held. Pending callbacks/helpers prevent cleanup and further verification; rejection does not prove application shutdown or CLI process exit. Managed application close has a five-second failure bound and unknown closure retains resources. Forced termination, unreadable ownership or unknown loaded state can retain resources on the disposable runner; neither cancellation nor `app.close()` proves process absence.

Managed protocol rejection emits only an allowlisted operation/reason, bounded transport byte counts and terminal status to `managed-protocol.json` in the sample failure artifacts. Empty responses additionally classify fixed Node module-loading and sudo authentication/environment diagnostic signatures, or remain `empty-response` when no signature matches. These categories describe observed transport text; they do not establish the hosted failure cause, helper-operation completion or privileged-writer absence. Receipt contents, helper stdout, request and environment dumps are excluded. Unknown responses also retain `managed-bootstrap.txt`, a separate observation of at most 1024 UTF-8 bytes from the transport-bounded helper stderr. Control/ANSI text is neutralized; operational paths, URLs, assignments, authorization and sensitive named fields are redacted. The capture boundary is the reviewed fixed sudo/Node/private-module command, its operational-only environment and isolated noncredential request. This boundary limits possible inputs; arbitrary secrets in free text cannot be exhaustively recognized. Unknown text is an observation for investigation, not authenticated operation or cleanup evidence. The diagnostic write has a 500ms failure bound. Diagnostic write failure preserves the original error and uncertainty; the retained receipt/resources still require independent safe recovery or disposable-runner disposal. Linux-only artifact and mount paths use POSIX semantics even when Node fixtures run on Windows.

Protected-path ownership/path/mode refusals include bounded typed metadata in the existing error text: observed UID/GID, numeric mode, link count, mode-derived type, expected type/mode and canonical equality (`same`, `different`, or `unchecked` when an earlier predicate refused). Fixed labels identify only `/` (`root`), `/var` (`var`), `/var/lib` (`var-lib`), `/etc` (`etc`), `/etc/apparmor.d` (`apparmor-dir`), `/var/lib/canopy-appimage-ci` (`managed-directory`), `/var/lib/canopy-appimage-ci/Canopy.AppImage` (`managed-original`), `/var/lib/.canopy-appimage-ci.json` (`managed-receipt`) and `/etc/apparmor.d/canopy-appimage` (`managed-policy`). Arbitrary canonical targets and caller paths are excluded. Metadata uses bounded own numeric data properties; diagnostic formatting failure preserves the original refusal. The existing typed failure envelope, six protocol metadata fields, redaction, retention and acceptance predicates remain unchanged. This observation identifies a refused predicate; it grants no operation or cleanup authority.

Loaded-profile identity refusals append at most 512 UTF-8 bytes of fixed-field metadata to the existing error text: trimmed attachment relation (`expected`, the fixed kernel sentinel `unknown`, or `different`), trimmed mode relation, primitive byte lengths, hash type and exact lowercase-64-hex-plus-newline format match. Profile contents, arbitrary attachment paths and hash values are excluded; formatting failure preserves the original refusal. The exact attachment, mode and kernel hash predicates still govern acceptance and cleanup. These observations describe the refused values and grant no recovery authority.

Node-only fixtures exercise the actual decision functions, private-worker IPC and bounded helper refusal. Process/filesystem/policy data in those fixtures are models; native parser arguments are captured, never executed. Separate real owned Node fixtures exercise successful spawn/exit/closure, timeouts, inherited worker pipes, transient errors and held cancellation/close promises. They cannot qualify real profile attachment or secure startup.

## Authority and qualification limits

The source now implements a scoped retained-spawn handshake for the sole existing first launch. Node's constructor notification supplies no PID authority; the successful event on the actual returned `ChildProcess` must match the exact direct-launch executable and arguments. A private nonce-bound observer checks parent/process birth and ordinary-user UID, then requests confirmation while the parent still retains that live handle. Duplicate, late, foreign, exited or disconnected handoffs invalidate accepted evidence while the authority protocol is open. Capture associates a matching command within the scoped interval; the audited caller must provide the sole launch with no concurrent matching spawn. The managed consumer requires referential equality between that captured object and Playwright’s returned `app.process()` before accepting retained authority; command matching alone supplies no independent association. Managed launch completion waits for the worker’s persisted sample before requesting stop, then requires final persistence acknowledgement and a clean worker exit plus drained IPC and process closure within the original ten-second observer deadline. Exit status is retained while unread final IPC is processed; a pending stop write, early closure or post-acknowledgement error refuses acceptance. A stop during an active managed sample permits that sample to finish before finalization. Capture remains active through the authority checks. Missing acknowledgement, IPC faults, late completion or forced worker termination refuse acceptance while the acquired application remains available to its caller for closure. The existing startup and launch/restart budgets are unchanged.

Fast-exec acceptance requires the original at the fixed root-owned, non-writable managed path with protected parents, matching original SHA-256 and stable file identity. It records `retained-spawn` authority, not a claim that `/proc` showed the original ELF before exec. Executable-file ownership is separate from the launch user's process ownership. Ordinary owned downloads still require seeing the native original before exec and can remain unknown when that observation is missed. Mounted ELF/ASAR hashes, FUSE identity, helper containment and effective context checks remain required.

Required parent, process or uniqueness failures clear accepted roots and samples. Final original-file validation is followed by another required launch-identity check before revocation/deadline checks and protocol closure. Completed snapshots record `finalizedAt`: the protocol closes synchronously before final serialization, so the report describes evidence through that boundary rather than live authority during persistence. Incomplete snapshots can retain an earlier observed sample and must be refused as completed evidence. Async mounted reads finishing after the sampling cutoff cannot add a sample.

This is source-only implementation with Node child/IPC and controlled Linux I/O fixtures. Successful managed AppImage installation, policy inheritance and cleanup have no genuine hosted qualification. Profile attachment through the original AppImage, Bash `AppRun` and mounted Electron, inherited effective context and secure first/restart require fresh independent source/security review and genuine exact-head hosted evidence. Unmanaged portability, native clean installation, upgrade/removal, desktop integration, unlocked keyring and signing trust remain pending.
