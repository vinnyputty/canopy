# Release discovery

**Settings → Updates → Check for updates** compares the running app version with compatible public releases in `vinnyputty/canopy`. It shows the current version/OS/CPU, selected release version, plain-text notes, matching installer filenames, check time and an **Open official GitHub Release** button. Downloads and installation are initiated by the user in their browser. Canopy never downloads or installs updates automatically.

Quiet notices default **off**. Opting in permits a check at launch and hourly while open, gated to at most one attempt per seven days. Notices are small, dismissible in-app controls; failures stay quiet. Dismissing a version suppresses further notices for that tag. Notices and attempt times survive restart. Development builds and invalid current versions do not run background checks. **Include prereleases** defaults off and is saved independently of notices; both the GitHub prerelease flag and SemVer prerelease suffix exclude a release from the stable channel.

## Selection and trust boundaries

Main-process Node HTTPS requests only the unauthenticated public `https://api.github.com/repos/vinnyputty/canopy/releases` endpoint. No provider authentication, workspace content, browser cookies or credential storage enters the request. Requests reject redirects, use a ten-second socket timeout and a fifteen-second total deadline, and invalidate queued and active checks on Cancel, preference changes, window destruction or quit. Requests capture their cancellation boundary before loading preferences and recheck it after each wait; later explicitly requested checks can proceed. Only the trusted app frame can invoke update IPC. The renderer has no network access.

The scan covers at most three pages of thirty releases. A single in-memory scan is reused for one hour across manual checks and channel changes; responses are limited to 2 MiB per page. SemVer ordering determines the highest eligible release, independently of list order. Publication, draft state, channel, positive uploaded asset size, explicit version/OS/CPU filename, and canonical official release/asset URLs must all pass. Source archives, ambiguous default builder filenames, checksums and other CPUs do not establish compatibility. Discovery recognizes explicit `Canopy-<version>-mac-<arm64|x64>.dmg|zip`, `Canopy-<version>-win-<arm64|x64>.exe`, Linux x64 `linux-x86_64.AppImage|linux-amd64.deb`, and Linux arm64 `linux-arm64.AppImage|deb` names. Recognizing a filename establishes discovery eligibility, not native qualification or artifact authenticity. Read the official notes and verify downloads before installing.

Empty, incompatible and failed scans have distinct inline messages. Invalid versions are not called up to date. Development builds warn that their package version may not describe the checkout; packaged versions absent from the scanned publications are labeled accordingly. Bounded scans explicitly disclose the limit. A failed refresh can retain one prior successful result for up to a week, labeled stale with its original check time, and never generates a notice. Reads expire stale selection and browser eligibility at exactly seven days from that original check time, including snapshots and notices-off background reads, without another network request. Ordinary failures pause checks for five minutes. GitHub `403`/`429` uses `Retry-After` and exhausted primary quota reset headers, with a minimum one-minute pause; there are no automatic immediate retries.

Preferences and weekly/dismissal timestamps use the existing atomic `Storage` writer in `updates.json` under app user data. Workspace saves and resets do not replace this file. Corrupt settings fail closed to notices off; persistence failure prevents a background network check or notice. Only preferences/timestamps/dismissed tag persist; public release bodies stay in a bounded memory cache.

Contracts checked against [GitHub Releases](https://docs.github.com/en/rest/releases/releases), [GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [Node HTTPS](https://nodejs.org/api/https.html), [Node HTTP cancellation/timeouts](https://nodejs.org/api/http.html), [Electron app version](https://www.electronjs.org/docs/latest/api/app#appgetversion) and [Electron browser handoff](https://www.electronjs.org/docs/latest/api/shell#shellopenexternalurl-options). The API version is `2026-03-10`. Pending release-publishing work is reference only; this feature neither publishes releases nor asserts that an eligible public build exists.

## Prepared native audit (requires a desktop test token)

`//:build` produces `dist/update-audit-main.cjs`, a separate fixture entry point omitted from packaged files. It uses local sample issues, synthetic releases, the real update service/IPC/renderer, and a recorded browser handoff. Production main accepts no environment override for release discovery. No fixture request reaches GitHub or a provider. The parent must explicitly supply an existing absolute disposable `CANOPY_USER_DATA` directory under the OS temporary directory or `/tmp`, with no credential file. The fixture rejects missing, non-temporary or credential-containing profiles before any runtime main import, launch/Auth loading or fixture writes, so rejected profiles cannot acquire inherited demo exit cleanup; do not reuse a real profile. Point a disposable copy of the built package's `main` at `dist/update-audit-main.cjs`. This preparation does not launch Electron.

After fresh review and explicit serialized desktop authorization, launch that disposable package on the target OS. `globalThis.canopyUpdateAudit` is available in the fixture main process for an authorized automation harness. `mode` selects `available`, `empty`, `incompatible`, `offline`, `rate` or `hold`; `advance(ms)` moves the service clock past cache/weekly/backoff boundaries. `requests` records page numbers, `browserHandoffs` records canonical links, and `releaseHeld` completes a held response. Unsupported architectures should report no compatible release. No real browser or installer is opened by this fixture.

- Check manual discovery with notices off: version, notes, matching CPU filename, canonical recorded handoff; verify no automatic download/install.
- Enable notices and restart the same disposable profile: verify persistence, at most weekly requests, quiet notice, dismissal and continued sample issue editing/navigation. Include prereleases, verify the prerelease label, then restore stable and verify the stable release.
- Advance beyond one hour; exercise empty/incompatible/offline/rate and confirm inline status, retained stale check time, no error dialog or notice, continued issue work and rate backoff.
- Hold initial preference loading or an actual preference write before a check receives a controller; Cancel, destroy the window or quit, then release the wait and confirm no request/notice starts. Request a new check after cancellation and confirm its version, notes and notice survive the old response. Also hold an active check; Cancel or change channel/opt-in, then complete/reject the old response. Verify no stale result/notice overwrites the new preference. Close the window while held; confirm cancellation.
- After an offline refresh, move the service clock to exactly seven days after the original success. Read Settings/update state or a notices-off background check; verify release/notes/check time disappear without network or notice, then explicitly check for a fresh matching version/body.
- Verify small-window scrolling to all Settings controls, keyboard focus/escape/return, notes wrapping, light/dark palettes, and dismissible notices without focus theft.

Native layout, desktop focus, real OS browser handoff, actual public artifacts and installation remain unqualified until separately authorized and recorded. Mocked transport/service/render tests and build/type/format/portable checks require no GUI, credentials, tags, releases or provider writes.
