# Windows release signing (DRAFT)

Windows public acceptance remains pending. The protected release path signs the NSIS installer, application executable and generated uninstaller through electron-builder 26's custom `win.signtoolOptions.sign` hook. PR and local builds remain credential-free unsigned test packages. A tag draft requires verified Windows signature metadata; public publication independently verifies the downloaded installer and extracted `Canopy.exe` on Windows before editing the release.

## Protected configuration

After fresh source review, configure the `windows-signing` environment with lead reviewers, prevent self-approval and restrict deployment to reviewed version tags. Configure `public-release` reviewers and reviewed dispatch branches separately. Environment protection requires repository settings; a workflow environment name alone does not restrict access. The signing job has `contents: read`; draft/publication jobs have `contents: write` and receive no signing credentials. No workflow dispatch signing path or PR signing secrets are provided.

The selected backend is a policy-approved PFX identity with a private key usable by Windows Authenticode. In `windows-signing`, supply environment secrets `WINDOWS_PFX_BASE64` and `WINDOWS_PFX_PASSWORD`. Set public environment variables `WINDOWS_SIGNING_SUBJECT` to the certificate's complete distinguished subject and `WINDOWS_SIGNING_THUMBPRINT` to its uppercase SHA-1 certificate fingerprint. This fingerprint pins the certificate, not the signature digest. Mirror these public identity variables in `public-release`. Missing values block the pipeline. Secrets belong only to the packaging step; packaged runtime checks and verification receive no PFX/password.

A suitable public identity has **not** been supplied or qualified. The [current CA/Browser Forum code signing requirements](https://cabforum.org/working-groups/code-signing/requirements/) require protected hardware for newly issued publicly trusted code signing private keys. Do not assume a newly purchased OV/EV certificate can be exported to a software PFX or weaken those requirements. This backend requires an issuer-approved identity/key policy and proof that the chosen key can lawfully be used this way. If the available identity requires a hardware token or cloud service, keep this release blocked and implement/review that backend before release; do not export its key to fit this pipeline. Private/test CAs do not establish public Windows trust.

The custom hook imports PFX bytes directly into an `X509Certificate2` using `EphemeralKeySet`, checks private-key availability, code signing EKU, exact subject/fingerprint and current validity, then calls `Set-AuthenticodeSignature` with SHA-256 and an HTTPS Authenticode timestamp service. It disposes the certificate and clears the byte buffer/environment in `finally`, including failures. It does not import into a certificate store, persist key files, pass credentials in arguments or attach credentials to reports. Each signing invocation is a separate finite PowerShell process. Secret strings also exist in the packaging process environment until that step exits; ephemeral certificate disposal is not a claim to erase every managed-memory copy. GitHub-hosted runners are disposable; cancellation terminates the process containing the ephemeral key. No store cleanup depends on a later workflow step.

Both the signing hook and artifact verifier require `Get-AuthenticodeSignature` status `Valid`, the pinned publisher certificate and a timestamp certificate. Windows SDK `signtool verify /pa /all /tw` independently checks every embedded signature under Authenticode policy. Tool failure, missing timestamp, current certificate expiry, publisher mismatch or changed bytes rejects the artifact. This deliberately rejects a currently expired signing certificate even if Windows would otherwise accept a historical timestamp. Certificate renewal requires fresh identity configuration and exact-byte qualification. Windows SDK SignTool, PowerShell 7 and `7z` must be present on the disposable Windows runner; missing tooling fails closed.

The verifier extracts NSIS's `app-64.7z` without running the installer, checks `Canopy.exe` against the same publisher identity, and removes only its owned temporary extraction directory on success or failure. `release-manifest.json` binds the Windows report to installer and executable SHA-256. Native evidence requires Windows `signingPolicy: "Authenticode signed and timestamped"`. Reports alone do not establish trust: public publication invokes real Windows verification again. macOS/Linux native and trust gates remain applicable.

## Guarded disposable lifecycle fixture

`tools/windows-lifecycle.ps1` is prepared for a fresh ordinary Windows 11 x64 account in a disposable VM. Do not execute until fresh source review, lead approval of native access and an exclusive lead-issued token. It requires clean reviewed source, an exact reviewed commit, `CANOPY_DISPOSABLE_WINDOWS_ACCOUNT=1`, `CANOPY_WINDOWS_NATIVE_TOKEN`, public identity variables and `CANOPY_SIGNTOOL`. The disposable-account variable is the operator's attestation, not automatic proof of VM isolation. The token is passed through the environment, never recorded in evidence. Provide distinct previous/new signed NSIS installers and exact SHA-256 values; both must verify against the configured certificate before installation. A certificate rotation needs a separately reviewed upgrade fixture/policy for the previous identity.

Example, after those prerequisites are met:

```powershell
pwsh -NoProfile -File tools/windows-lifecycle.ps1 -ReviewedCommit <reviewed-sha> -PreviousInstaller <previous-exe> -PreviousSha256 <previous-hash> -Installer <new-exe> -Sha256 <new-hash>
```

The fixture refuses existing Canopy processes, installation, registration, shortcuts or default profile. Installers run silently as the ordinary account with finite deadlines; NSIS is configured per-user, with no elevation, fixed installation location, retained application data and desktop/Start menu shortcuts. It verifies installed executable trust and shortcut targets, launches the installed app with a newly owned `CANOPY_USER_DATA`, upgrades, checks an owned profile marker, removes the upgraded installation, exercises a clean install of the current artifact with another owned profile, and attempts native uninstallation in `finally`. Only owned process trees are stopped. Existing profiles are never deleted. Partial installation without a usable uninstaller, timeout or incomplete removal fails and preserves the disposable VM for investigation. The fixture retains its owned sample profile and a new `lifecycle-report.json` even after failure; cleanup status and stage are recorded. Discard the VM after collecting evidence.

This fixture always records `nativeChecks: "pending"`: a responding process and retained marker do not prove interactive first launch, saved preferences or secure credentials. Windows Server packaged checks likewise do not qualify Windows 11 installation. Complete and record these acceptance tasks against the exact bytes before public release:

- [ ] Real policy-approved publisher identity; successful signing, signature rejection and failure/cancellation cleanup on Windows, with no persisted private key/store state or credential leakage.
- [ ] NSIS wizard clean install under a fresh ordinary Windows 11 account; welcome screen, demo, quit/relaunch, expected Installed apps entry, icons, desktop and Start menu launch behavior.
- [ ] An explicit previous/new version pair; saved roots and appearance/view preferences retained, authorized test credentials retained and usable, correct new executable installed, no duplicate registrations/shortcuts.
- [ ] Installed apps/native NSIS uninstall; executable, registration and shortcuts removed, retained sample user data documented; reinstall succeeds.
- [ ] Download-origin trust/UAC/SmartScreen observations and final native evidence, reviewed source, protected environments and lead approval.

A newly published signed app may initially trigger SmartScreen's reputation warning. Signing identifies the publisher and protects integrity; it does not guarantee that SmartScreen suppresses prompts. Record the ordinary download/install experience without bypassing trust controls to claim acceptance. See [Microsoft's SmartScreen overview](https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/).

## Tool contracts

The pinned electron-builder **26.15.3** implementation supports `win.signtoolOptions.sign` and `signingHashAlgorithms`; use its [v26 contract](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/), rather than the newer `win.sign` schema. Microsoft documents [in-memory ephemeral PFX keys](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.x509certificates.x509keystorageflags), [Set-AuthenticodeSignature](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/set-authenticodesignature), [Get-AuthenticodeSignature](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/get-authenticodesignature), and [SignTool verification](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool). GitHub documents [environment review and secret access](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). These contracts were checked on 2026-10-02; real PFX/PowerShell interoperability and Windows qualification remain pending.
