# Windows release signing (DRAFT)

The protected release path uses **Microsoft Artifact Signing Public Trust** through the pinned native SignTool dlib SDK. The service generates and uses private keys inside its managed hardware security modules; private keys are not exported, imported on the runner or accepted as software PFX input. The NSIS installer, executable and generated uninstaller use the same durable publisher/profile policy. PR/local packaging remains credential-free and unsigned. Real service/native acceptance remains pending and blocks public release.

## Protected service configuration

Configure the `windows-signing` environment with lead reviewers, prevention of self-approval and restrictions to reviewed version tags. Configure `public-release` reviewers and reviewed dispatch branches separately. A YAML environment name does not configure repository protection. The signing job has `contents: read`; draft/publication jobs have `contents: write` and receive no signing credentials. The backend requires the repository's `ci.yml` tag-push origin, hosted Windows, an exact package-version tag, and matching checked-out/tagged source commit. No PR or manual-dispatch signing path is provided. Process environment checks supplement the protected workflow; they cannot independently authenticate an operator who can spoof environment values.

After the real service identity has been approved, supply public environment variable `WINDOWS_SIGNING_POLICY` as JSON with exactly these fields:

```json
{
  "service": "Microsoft Artifact Signing",
  "profileType": "PublicTrust",
  "auth": "EnvironmentCredential",
  "endpoint": "https://eus.codesigning.azure.net",
  "account": "<approved-account>",
  "profile": "<approved-profile>",
  "profileEku": "<approved-durable-public-profile-EKU>",
  "subject": "<complete-certificate-distinguished-subject>",
  "tenantId": "<approved-tenant-UUID>",
  "clientId": "<approved-service-principal-UUID>"
}
```

This is a schema example, not a configured identity. Only Microsoft's documented regional HTTPS endpoints are accepted, without paths, credentials, alternate hosts or ports. `PublicTrustTest` and `PrivateTrust` are rejected. The full subject and durable EKU must come from the approved **Public Trust** certificate profile. Bind the approved account, endpoint and profile to this EKU during identity review. The service principal must have only the Artifact Signing Certificate Profile Signer role scoped to that certificate profile. Public variables `WINDOWS_SIGNING_TENANT_ID` and `WINDOWS_SIGNING_CLIENT_ID` must match the policy. The packaging step alone receives secret `WINDOWS_SIGNING_CLIENT_SECRET`. No OIDC token, login cache, CLI authentication, machine certificate or interactive fallback is used; SDK metadata excludes every alternative credential in the pinned client. Certificate-based/user/password authentication and alternate authority hosts are rejected. Mirror the public policy in `public-release`; no secret is needed there.

The source prepares `Microsoft.ArtifactSigning.Client` **1.0.128** directly from NuGet into newly owned runner storage, checks its pinned package SHA-256 and uses `bin/x64/Azure.CodeSigning.Dlib.dll`. The runner needs compatible x64 Windows SDK SignTool, .NET 8 runtime and the client's native runtime prerequisites. No installer/configuration fallback is performed. Missing tools or prerequisites fail closed. Preparation and cleanup are separate from the secret-bearing packaging step; only public SDK files and non-secret metadata are written. The owned metadata directory is removed on signing, verification or command failure. Signing/authentication occur in bounded owned process jobs, with no credentials in command arguments, native output or artifacts. Child credential copies are discarded after each signing call; the packaging step's environment exists until its process exits. Service keys remain remote; no local certificate lifetime or store cleanup is involved.

## RFC 3161 and actual public trust

The custom electron-builder **26.15.3** `win.signtoolOptions.sign` hook invokes the native SDK with `/fd SHA256 /tr http://timestamp.acs.microsoft.com /td SHA256 /dlib … /dmdf …`. This is Microsoft's documented SignTool RFC 3161 route and timestamp endpoint. Timestamp transport uses the documented HTTP endpoint; the signed timestamp token is authenticated by Windows trust verification. PowerShell `Set-AuthenticodeSignature` is not used. The old in-process/private-key entry point fails closed.

Verification requires an embedded Authenticode signature, a timestamp, `Get-AuthenticodeSignature` status `Valid`, and independent `signtool verify /pa /all /tw`. `WinVerifyTrust` additionally applies Authenticode policy with online chain revocation checks, without lifetime-signing or cache-only flags. It reads the verified signer/countersigner chains and timestamp verification instant. Both chains must end at the pinned Microsoft Identity Verification Root Certificate Authority 2020 SHA-256, not an arbitrary machine-installed private root. The leaf must contain the code-signing EKU, Microsoft's Public Trust EKU and the configured durable profile EKU, and match the exact approved subject. The verified timestamp instant must be within both leaf and TSA certificate validity periods. Native errors, malformed metadata, unsigned files, private/test chains, missing timestamps, wrong publisher/profile, altered bytes or unavailable revocation information fail closed.

Cloud leaf certificates rotate daily and are short-lived. The policy pins the durable profile EKU and subject, not a permanent leaf thumbprint. Exact leaf/TSA fingerprints, validity periods, verified timestamp, chain roots and file hashes are retained in per-artifact evidence. A historically timestamped signature remains eligible after leaf/TSA expiry if native current trust/revocation verification passes. Leaf rotation between installer/executable signatures is accepted; re-verification of an existing artifact requires its recorded leaf and executable bytes.

The verifier extracts the NSIS payload without executing the installer. Extraction and SDK verification run in finite owned jobs; only owned temporary extraction directories are removed. A changed installer during verification is rejected. The manifest binds service policy and executable/installer identities to exact SHA-256. Public publication independently verifies downloaded signatures again; signature reports or private/test fixtures alone cannot establish trust. Existing macOS/Linux/tag/version/native/checksum gates still apply. Windows native evidence requires `signingPolicy: "Authenticode signed and timestamped"`.

## Guarded disposable lifecycle fixture

`tools/windows-lifecycle.ps1` adapts arguments to the testable Node controller in `tools/windows-lifecycle.mjs`. Run only after fresh source review and lead-approved access/token to a disposable ordinary Windows 11 x64 account. Set `CANOPY_DISPOSABLE_WINDOWS_ACCOUNT=1`, `CANOPY_WINDOWS_NATIVE_TOKEN`, the public `CANOPY_WINDOWS_POLICY` JSON and `CANOPY_SIGNTOOL`. Supply an exact clean reviewed commit, distinct previous/current signed NSIS installers and SHA-256 values. Signing credentials are refused. Both containers and embedded executables must pass actual trust checks before installation.

```powershell
pwsh -NoProfile -File tools/windows-lifecycle.ps1 -ReviewedCommit <reviewed-sha> -PreviousInstaller <previous-exe> -PreviousSha256 <previous-hash> -Installer <new-exe> -Sha256 <new-hash>
```

Preflight derives the pinned builder's UUID-v5 app GUID, checks both installation and uninstall keys in **HKCU/HKLM, 32-bit/64-bit views**, including partial keys without `DisplayName`, and scans matching uninstall registrations. Any registration is a refusal, including custom `InstallLocation` and machine installs. It resolves actual UserProgramFiles through `SHGetKnownFolderPath` without creating it, checks redirected/default/machine install directories, user profiles, current/common desktop/Start menu entries and renamed shortcuts targeting Canopy. Existing processes or unresolved snapshots also block the first installer. Disposable-account attestation does not replace these checks.

Every native operation has a finite Node deadline. Applications/installers/tools start suspended, are atomically assigned to non-breakaway Windows Job Objects at creation through `PROC_THREAD_ATTRIBUTE_JOB_LIST`, and retain original process/job handles. Shutdown uses the owned job or a retained still-suspended process handle, never stale PID/name/tree killing. The helper confirms the whole job is empty and the retained main process has exited. Failed/unknown ownership or remaining Canopy processes blocks upgrade, uninstall and any next installer; profiles/VM are retained. This prevents handing stale processes to NSIS's process-closing/name fallback. Compiler/parser-only Windows CI controls do not invoke native operations. The separate Node-only process job harness requires explicit disposable-account/native-token authorization and is not automatically run.

The controller checks installed executable hash and exact artifact leaf, registry/shortcut targets, preliminary first-launch survival and confirmed owned shutdown; upgrades with an owned sample profile, checks its marker, removes the upgraded installation, then clean-installs the current artifact using another owned profile. Installer/uninstaller operations have 90-second waits plus bounded shutdown; helper requests retain the original 120-second outer deadline. Uninstall verifies registration, application and shortcut removal and retained sample data. No profile is deleted. Primary failures and secondary cleanup/ownership/evidence failures are recorded separately in a newly owned `lifecycle-report.json`, environment restoration is recorded, and the original error is rethrown with that report. Cleanup cannot mask the primary failure. A forced helper/session termination leaves job kill-on-close protection; unknown completion remains a failed, retained VM requiring investigation.

The fixture always records `nativeChecks: "pending"`. Automated process survival/profile markers do not prove interactive welcome/demo, preferences or authorized credentials. Complete these exact-byte acceptance tasks before publication:

- [ ] Approved Public Trust service identity/profile, scoped role and protected workflow configuration; real SDK authentication/signing, RFC 3161 timestamps, negative trust/revocation/tamper checks and failure/cancellation cleanup with no credential leakage.
- [ ] Windows parser/compiler and explicitly authorized owned-process harness; guarded Windows 11 native lifecycle fixture and failure/cleanup scenarios.
- [ ] Ordinary NSIS wizard clean install, welcome/demo/quit/relaunch, correct Installed apps entry and version, icons and desktop/Start menu launch behavior.
- [ ] Explicit previous/new upgrade pair with saved roots/preferences and authorized test credentials preserved; correct current executable and no duplicate registrations/shortcuts.
- [ ] Installed apps/native uninstall, retained sample data and successful reinstall; normal download-origin SmartScreen/UAC observations.
- [ ] Exact-byte native evidence, full platform matrix, fresh independent review and lead approval.

A newly published signed app may still show SmartScreen's initial reputation prompt. Signing identifies the publisher and protects integrity; it does not guarantee prompt suppression. Record the ordinary download/install experience without bypassing trust controls to claim acceptance.
