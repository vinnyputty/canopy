# Jira provider notes

Canopy uses Jira Cloud REST API v3 through an OAuth request function already scoped to `api.atlassian.com/ex/jira/{cloudId}`. Searches use the enhanced `POST /rest/api/3/search/jql` endpoint. Tree loading follows every `nextPageToken`; the open-issue picker requests 25 matches at a time and loads further pages on demand. Picker queries include escaped literal text and a generated trailing wildcard when the query ends in a letter or number, so partial words can match. User-entered metacharacters stay escaped. Jira supplies candidates by update time; Canopy ranks the loaded set by exact summary, summary prefix, substring, then other text matches, with current project and update time as secondary signals. The picker labels incomplete sets explicitly because later pages may contain stronger matches. Query changes and closing the picker abort its request; stale responses cannot replace a newer search. See Atlassian’s [text search syntax](https://support.atlassian.com/jira-software-cloud/docs/search-for-work-items-using-the-text-field/) and [enhanced search API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/).

Jira search is eventually consistent. Canopy sends `reconcileIssues` with the last 50 changed issue IDs per authenticated connection for up to five minutes after their most recent write. Reads do not extend that window. A returned issue whose edited fields disagree with the confirmed write is checked with a direct issue read, so current remote values take precedence. A 404 from that reconciliation read omits the missing issue from tree and search results; other direct-read errors still fail the request. Successfully completed portions of a partially failed edit are tracked too. An explicit unsupported-parameter response retries without reconciliation; authentication, permission, and other failures remain errors. After expiry or eviction, search becomes authoritative. Provider replacement on reconnect or account change clears this session-local tracking. See Atlassian’s [search and reconciliation guarantees](https://developer.atlassian.com/cloud/jira/platform/search-and-reconcile/).

The issue tree follows Jira's `parent` field one level at a time. This supports every hierarchy level exposed by the site rather than assuming a fixed epic/story/subtask shape. Issue links are shown as nonrecursive references on the issue that contains them because links can form cycles and do not define ownership.

Sibling dragging and rank undo call Jira Software's `PUT /rest/agile/1.0/issue/rank`. Placement uses `rankBeforeIssue` or `rankAfterIssue` to restore the original neighbor. It requires the Jira Software rank scope and a Rank field; Canopy rejects moves between different parents and moves of the tab root. Sites without an available Rank field display children in stable issue-key order and report that fallback in the tree warnings. Jira can still reject a valid sibling move because of project permissions or rank configuration, including a partial failure reported with HTTP 207.

Reconciliation guarantees apply to specified issues, not the complete sibling order. Canopy preserves up to 50 recent successful sibling moves per connection for at most five minutes each, replaying them over lagging search order across overlapping trees. Moves for a sibling group retire together when the unmodified search order agrees with their combined placement. Issue eviction also retires its moves. A genuine remote reorder may be temporarily hidden during this window; after retirement, Jira ordering takes precedence. Missing or reparented issues are not inserted into their former sibling group.

Rank handles require a successful Rank query and issue-specific Schedule Issues and Edit Issues grants from `POST /rest/api/3/permissions/check`, checked in batches of up to 1,000 issues. Missing grants hide the corresponding handles; failed capability checks hide handles and explain that availability is unknown. This follows Atlassian's [ranking requirements](https://support.atlassian.com/jira-software-cloud/docs/rank-an-issue/) and [bulk permission API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-permissions/#api-rest-api-3-permissions-check-post). A project type alone does not determine rank support. Jira remains authoritative when a rank write is submitted.

Column sorting is local to each sibling group. Priority order is loaded lazily through a JQL query with one representative issue per priority and `ORDER BY priority DESC`, using the existing search scope. The order is cached for the connection and set of priorities for the current app session. A failed lookup keeps Jira order visible with an explicit retry action. Missing assignees and priorities sort last in both directions; ties use natural issue-key order. Sorting by another column disables rank dragging and keyboard ranking.

Table views are saved per connection and root, independently of tab lifetime. Connection defaults and root overrides include columns, widths, sort, filters, text size, row spacing, and status-transition sharing. Each customized root keeps a complete view until reset to its connection's current default.

Priority metadata, assignee search, and workflow transitions load independently, each with its own error and Retry action. Provider caches live for the connection’s app session and are discarded on disconnect or credential replacement. Concurrent matching requests share their results. Priority metadata is issue-specific. By default, a Jira root prefetches a transition graph for each project and issue type and shares choices among its issues of that type. Full graphs require Jira workflow-view or admin permission; otherwise Canopy prefetches each issue-type/current-status pair present in the tree and loads unseen statuses when first used. The root’s View menu can disable sharing. Status changes select the cached choices for the new status. A rejected selection or return from Jira refreshes that issue’s choices; other edits preserve unrelated choices. There is no timed cache expiry.

The assignee picker immediately shows up to 100 recently seen identities for the connection, seeded from loaded issues and user results. These are suggestions, not shared assignment grants: selecting a person checks their account ID against the current issue before submitting. Search and scrolling to the end (or Load more people) fetch additional candidates. The [assignable-user API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-user-search/#api-rest-api-3-user-assignable-search-get) filters within a requested candidate window; a short or empty result does not mean discovery is complete. Canopy advances windows of 100 through Jira’s first 1,000 users and explains that discovery may remain incomplete. The identity cache does not make an exhaustive directory available.

The assignee picker keeps **Assign to me** above the search results, using the active connection’s signed-in account. It shows **Assigned to me** when that account already owns the issue. The action waits for account identity and validates issue-specific eligibility before using the usual optimistic update, cross-tab synchronization, rollback, and undo. Account lookup failures use the connection’s Retry action; eligibility and assignment failures remain visible in context.

A transition whose screen requires extra fields is displayed but marked as requiring fields. Canopy checks fresh transition metadata before submitting and refuses transitions with unsupported required fields.

Jira omits issues the signed-in user cannot browse. Canopy can report an inaccessible root directly, but Jira does not reveal inaccessible descendants, so it cannot distinguish them from absent children.

The renderer applies supported edits optimistically across tabs sharing a connection. Field writes are serialized per issue, ranking per connection. Tree refreshes wait for active editors and pending writes on their connection. Responses reapply writes completed after the request began; closing a tab invalidates its outstanding responses. Failed writes remove only their own optimistic change.

Undo is session-local and checks freshly fetched issue values or sibling order before writing. Status undo requires a currently available transition back with no required fields. Rank undo requires fresh supported ranking permissions for the moving issue, including when another display sort is active. Unsupported inverses and changed remote state are reported and skipped; transient failures remain retryable. While local rank placement is still being preserved, undo reports that Jira is catching up and remains retryable; it validates ordering only after a tree reports unmodified Jira order. These checks are best-effort: Jira does not expose an atomic compare-and-set for these operations, and its search results can lag completed writes.

Space on a focused tree row opens a read-only preview with its description, the ten newest comments, and linked issue references. Preview data loads on demand; moving the tree selection updates an open preview, and closing it restores focus without changing tree scroll. Comment errors leave the description and links available and can be retried. Jira descriptions and comments render paragraphs, headings, nested lists, emphasis, code, and safe HTTP links from structured text. Unsupported nodes retain readable text where available; attachments and rich media remain in Jira. Missing content shows an empty-state message, while loading errors keep their Retry action. Comment ordering and permissions follow the [Jira comments API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-comments/).

Permission failures remain visible with a Retry action. Responses for a previously selected issue or connection cannot replace the current preview, even when two connections use the same issue key. Unsupported formatting remains plain text; the preview does not support editing descriptions and comments.

Relationship labels describe the selected issue's direction (for example, “blocks” or “is blocked by”). References can be previewed or opened as a separate tree and are never traversed as hierarchy children. Each row's context menu supports copying its key, title, Jira link, or Markdown work brief and opening Jira. Right-click, the row actions button, or Shift+F10 opens that menu. The preview also offers **Copy work brief**; review the exact Markdown before copying. Jira descriptions are converted from their document structure, retaining headings, lists, links, and code blocks. Unavailable parent paths or dependency links are marked in the brief.

The preview's resize handle supports dragging, Left/Right arrows, and Home/End. Its preferred width is saved across launches; the pane fits within the window. Escape closes a row menu before closing the preview. Preview visibility is temporary and resets on a tab change.

Transitions requiring additional fields offer a keyboard-accessible Open in Jira action for that issue and connection. Canopy keeps the transition unavailable for submission and preserves tree selection and position. Returning to Canopy refreshes the originating tree and invalidates issue picker choices, including when status is unchanged. The shared refresh scheduler waits for offline or pending edits to clear and queues a follow-up if an earlier request is still running.

Identical in-flight GET requests and read-only search/permission POST requests share one transport request per connection. Request bodies and page tokens remain distinct; cancelable search calls run independently. Successful responses are not cached by the transport. Mutations advance the sharing generation at dispatch and settlement so later reads cannot join stale requests.

A Jira 429 pauses every operation on that connection, including manual and focus refreshes and writes. `Retry-After` accepts seconds or an HTTP date; absent or invalid values use exponential delays from 30 seconds to 15 minutes. A successful recovery resets the fallback delay. Writes are never queued or replayed by this recovery mechanism. Refresh failures retain the last successful tree and read the shared retry deadline for the sync-status UI; the active tree resumes first, with background trees retaining their adaptive schedule. Disconnecting or replacing credentials discards transport state.

## Changes since last seen

Canopy saves a local last-seen baseline after a successful tree load for up to 1,000 issues in each of the 12 most recently loaded roots. Later refreshes flag confirmed field changes and Jira's last-activity timestamp, which includes comment updates. Jira comment counts and recent comment links load when the preview opens, so the tree does not download comment bodies for every issue. The preview shows previous and current field values and links comments whose creation times confirm they arrived after the baseline. A count increase with unavailable recent comments is labeled as such. Mark an issue seen in the preview or the root from the toolbar. Opening a preview and switching tabs preserve unread state; failed refreshes retain the baseline. Canopy's confirmed edits update their written field baselines; a later activity timestamp may still reflect the edit. Development updates and full provider history are unavailable in this view.
