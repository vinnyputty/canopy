# Large-tree performance audit

The benchmark executes production Jira/GitHub parsers and hierarchy traversal against deterministic fake transports, plus the production tree, filter, reconciliation, saved-view, and shared refresh functions. It uses a 9,901-issue wide root, a 10,101-issue three-level hierarchy, and a 2,001-issue chain for each provider. The chain is an adversarial depth stress fixture, not a claim about ordinary Jira hierarchy depth. Fields include realistic summaries, assignments, statuses, priorities, activity, links, labels, comments and unused GitHub body text. The six-root saved view deduplicates and naturally sorts real parsed issues.

Run from the repository with dependencies installed:

```sh
node --expose-gc tools/benchmark-large-trees.mjs
CANOPY_PERF_LATENCY_MS=2 node --expose-gc tools/benchmark-large-trees.mjs
```

To compare a baseline, archive its `src` into a disposable directory and set `CANOPY_PERF_SOURCE` to that directory and `CANOPY_PERF_HEAD` to its full commit ID. The same fixture/harness loads production modules from that directory. CPU measurements report the median of five synchronous runs; provider loads and the concurrent six-root refresh report one wall-time sample. The refresh has eighteen consumers but six real provider reads. The optional delay is synthetic round-trip latency, not live-provider timing. Heap deltas are GC-retained Node data measured after allocating wire fixtures; they exclude fixture construction, Chromium and Electron. Reconciliation includes cloning the received snapshot. No benchmark number is a browser scroll, paint or interaction measurement.

The initial `30c57db` measurements justified linear parent-cycle classification and reuse of a collator for saved-view sorting. Provider request counts justified progressive delivery and cancellation during long reads. The first native paired run on main `af0808d` versus reviewed `d87172d` failed overall (5 of 12 scenarios completed). The observer-removed Jira control still had about 264,000 DOM elements and 366 ms median scroll-frame intervals in both builds. Both deep control renderers crashed with reason `crashed`, exit code 11; the baseline also reported a stack overflow. These single samples justify investigating rendering and scroll work; they do not establish an OOM cause or a candidate-only regression.

Rows now use a flat sibling DOM with explicit ARIA level, sibling position and sibling count, keeping their rich controls, stable keys and logical indentation. Visible traversal, filtering, counts, sorting, navigation lookup, editing-order retention and Next Tasks traversal use explicit stacks. Next Tasks ancestry is built when its pane is open. Native scroll offsets are recorded immediately for navigation/restoration and saved after 180 ms idle, without updating rich App state on every scroll event. Historical navigation restores its requested offset. All visible logical rows remain mounted; this change does not bound DOM count or demonstrate acceptable native latency. The new exact pair must measure whether further windowing is necessary.

Snapshot admission continues to charge distinct confirmed, rendered and gate snapshot identities plus distinct displayed issue objects not aliased by those snapshots. Eviction releases gate and displayed graph owners. Editor connections, active real/saved consumers, child drafts, selection, bulk work and pending writes keep their existing protection. Serialized UTF-8 payload admission is not a heap/RSS cap: node wrappers, task ancestry, traversal temporaries, React state and DOM allocations remain outside it, and protected owners may exceed the budget. Unread baselines retain their separate existing bounded policy; offset refs contain UI numbers only.

## Desktop acceptance (pending)

Source review precedes changed GUI acceptance. All Electron/GUI/clipboard work requires a fresh explicitly granted exclusive desktop token. Historical paired Node artifacts remain `30c57db` versus `9cbfc13`; their pinned modules and measurements are unchanged. They are not measurements of this review fix or native UI timings.

`tools/prepare-perf-desktop.mjs` builds a clean, committed candidate and an explicit exact `CANOPY_PERF_BASE` commit (current comparison main `5cdf719fac9650f9ef31d41d880942af657ff98b`) into isolated temporary archives without launching Electron. Both sources use identical candidate fake-transport fixtures and audit observers, with real source-specific providers, preload, IPC handlers and renderer. The manifest records exact source IDs, audit harness hashes, output bundle hashes and expected counts computed with each source's production provider/filter/saved-view functions. It requires complete fixtures before preparing the pair. The preparer also writes the full manifest SHA-256. The driver requires fresh approval naming that exact base, candidate and manifest digest, validates complete paired source/scenario ownership, and checks every required harness and bundle hash before importing desktop tooling:

```sh
CANOPY_PERF_BASE='5cdf719fac9650f9ef31d41d880942af657ff98b' node tools/prepare-perf-desktop.mjs
CANOPY_PERF_APPROVED_BASE='<freshly approved exact base>' CANOPY_PERF_APPROVED_MANIFEST_SHA256='<freshly approved manifest digest>' CANOPY_PERF_PAIR='<printed manifest path>' CANOPY_PERF_APPROVED_HEAD='<freshly source-approved exact candidate>' CANOPY_DESKTOP_TOKEN='<explicitly granted token>' CANOPY_ELECTRON_PATH='<Electron executable>' node tools/perf-desktop.mjs
```

The historical af/d871 and af/150 pairs retain their original source IDs, bytes and evidence. They are not measurements of the current main integration. The audit alternates base/candidate for every Jira and GitHub wide, tiered and deep root, each with a fresh disposable profile and one initial tree. Each scenario then loads and refreshes the three-root saved view. The issue counts are 9,901 / 10,101 / 2,001; expanded, collapsed, filtered and saved-view DOM counts come from the exact-source expected-count manifest. Each operation and assertion uses an explicit finite 180-second budget, including initial visibility, full completion, UI count and paint opportunities. Completion requires an IPC-delivered full snapshot with the expected normalized issue count and `incomplete=false`, plus the corresponding UI row count. Saved refresh arms a manual generation and clicks Refresh in one renderer turn after verified IPC idle, then identifies the first subsequent request ID per root. Only full deliveries bearing that generation satisfy refresh completion. The next automatic poll remains recorded separately; its Cancel button does not invalidate a completed manual request. A busy root that never becomes idle, a missing manual request, an incomplete/error response or a missing full UI state fails the audit. Identical fixture contents and row counts cannot independently identify the exact React commit applying a refresh; the audit records IPC completion followed by the observed full-count UI and RAF opportunities. Errors, incomplete results and disappearance of Cancel controls cannot stand in for completion. First partial IPC delivery and the first smaller DOM commit before the full UI commit are reported separately; a source without partial progress records that absence. The saved-view selector uses main #83's accessible `Saved view: Large roots` name.

Compact audit telemetry records main provider start/progress/completion and call timestamps, preload IPC request/progress/delivery, DOM mutation commits, RAF opportunities, frame intervals and long tasks. Every initial load, tree filter/clear, scroll, collapse/expand, saved-view load and saved refresh has a phase marker and DOM count. Filter and refresh wall times end after the expected state and two RAF opportunities. Main and renderer monotonic timestamps retain their time origins for correlation; cross-process correlation is approximate. Transport-call counts and timestamped per-root events permit phase deltas, including all three saved-refresh roots.

Memory sampling uses the same 250 ms cadence plus phase boundaries for both builds, capturing Electron process metrics and main process memory. Raw per-process samples permit residency comparisons, sampled maxima and phase growth; they do not guarantee the true peak, isolate snapshot bytes or imply a heap reduction. Summed process working sets can count shared pages more than once. The first memory sample follows launcher connection, so early startup allocations can be missed. IPC timing includes queueing, provider work and serialization; DOM observer delivery approximates commit visibility, and RAF intervals/long tasks measure main-thread responsiveness. RAF is a paint opportunity, not a compositor paint measurement. Filter wall time includes Playwright input, application handling, polling and RAF waits; it is not isolated renderer or IPC timing. The identical instrumentation adds overhead and compact telemetry allocations to both builds. Synthetic 2 ms fake-transport latency is not live-provider latency. Deep chains are a stress scenario. Repeat entire paired runs for distributions; single samples are not a performance verdict.

The driver verifies the candidate harness hashes, including its lifecycle dependency, and writes `/tmp/canopy-perf-90-desktop.json` with failures and partial telemetry. The main fixture observes `render-process-gone` before window launch; the driver captures bounded stderr, page errors and renderer crash events. Failure diagnostics have finite deadlines. Each launch gets a new disposable profile, and the reviewed `AuditOwner`/`finishAudit` helper proves owned-process absence before deleting it; uncertain ownership retains the profile and records a cleanup failure. The helper is copied unchanged from the lead’s reviewed native control artifact; this reuse conveys no Windows qualification. Primary failures precede diagnostic/cleanup faults. Preparation/build and source checks do not validate native navigation or timings. The old failed pair and observer-removed control remain immutable evidence. The changed source/audit pair has not been launched and requires fresh source review and an exclusive token.
